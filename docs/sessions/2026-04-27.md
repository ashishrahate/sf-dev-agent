# Wave 8 slice 2b — AWAITING_APPROVAL + AgentLoop.resume()

User asked for the "task plan approved flag" + "resume with redisplay." Slice 2b ships both: the missing AWAITING_APPROVAL state transition AND a resume entry point that picks up at any non-terminal status.

## The transition gap

Before 2b, the agent went planning → submit_plan → approval prompt → executing/failed without ever transitioning to `AWAITING_APPROVAL`. A crash mid-prompt left the row stuck at status=planning, indistinguishable from "still planning" — resume couldn't tell which dispatch path to take.

Slice 2b inserts `_transition(TaskStatus.AWAITING_APPROVAL)` between Phase 1 end and the human prompt. The "modify" path also re-transitions PLANNING → AWAITING_APPROVAL after each revision pass.

## Refactored `run()` into composable phases

`run()` previously contained the whole plan → approve → execute flow inline. Resume needed to call sub-segments of that flow without duplicating logic. Extracted three helpers:

- `_run_planning_then_execution()` — Phase 1 → Phase 2.
- `_run_approval_then_execution()` — present plan → prompt → Phase 2 (also handles "no plan was produced" path).
- `_run_execution_only(append_transition_message: bool)` — Phase 2; the "Plan approved. Proceed with execution." message is only appended when transitioning IN from approval, NOT on resume from EXECUTING (it's already in the seeded transcript).

The `append_transition_message` flag is the load-bearing detail. Without it, resume from EXECUTING would duplicate the message.

## `AgentLoop.resume(task_id, ...)` classmethod

Loads the persisted task + conversation, rehydrates `Task.plan` from `plan_json`, dispatches by status:

- terminal (complete/failed/rolled_back) → short-circuit, return Task with summary.
- executing → Phase 2 only (skip Phase 1).
- awaiting_approval, OR planning + plan saved (the crash window) → redisplay plan + reprompt.
- planning / received → continue Phase 1, then Phase 2.

Cross-tenant resume is rejected with `ValueError`. Unknown task_id raises. `Task.plan` rehydration uses the existing `_parse_plan` helper (the saved `plan_json` is the original `tool_input` from `submit_plan`).

# Wave 8 slice 2c — decay scoring on `MemoryStore.recall`

Smallest of the slice 2 follow-ons. Pure ranking nudge — recall now blends cosine similarity with the row's usage history.

## What changed

`MemoryStore.recall(decay=True)` (default on) computes:

```
adjusted_score = cosine * (1 + decay_factor)
decay_factor = recency_penalty + usage_boost
```

- **Recency penalty.** `exp(-age_days / 30)` decays from 1.0 (just accessed) toward 0 (forever stale). The penalty equals `-RECENCY_ALPHA * (1 - decay)`, capped at -10% for forever-stale rows.
- **Usage boost.** `1 - exp(-access_count / 5)` saturates from 0 (never used) toward 1 (used many times). Boost equals `USAGE_ALPHA * saturating`, capped at +5%.

Adjusted score is clipped to [0, 1] so the orchestrator's score-range contract holds. The cosine remains dominant — decay is a tie-breaker, not a replacement (asserted by a test where a high-cosine stale row still beats a low-cosine fresh one).

Module-level constants (`DECAY_HALF_LIFE_DAYS`, `DECAY_RECENCY_ALPHA`, `DECAY_USAGE_K`, `DECAY_USAGE_ALPHA`) make the magnitudes tunable without code surgery.

## Why this didn't break existing tests

Within a single test run, all memories are saved at roughly the same time and have access_count=0. The decay nudge is uniform across candidates, so relative ordering is preserved.

For tests that do exercise decay, a `_age_memory_in_days` helper backdates `last_accessed_at` directly via SQLite update — no need to wait 30 days.

# Wave 8 slice 2d — automatic compaction + `memory_supersede`

Bigger of the slice 2 follow-ons. Detects clusters of similar memories within (scope, type), surfaces them to the agent, lets the agent propose merges, persists the supersedes link.

## `MemoryStore.find_merge_candidates`

Pairwise cosine within (scope, type), connected-components BFS at threshold ≥ 0.85. Returns `MergeCandidate(type, members, average_similarity)` clusters of size ≥ 2 ordered by tightness (mean pairwise similarity).

Algorithm details:
- Pre-grouped by type — clusters are always type-homogeneous (a `feedback` and a `project` row about the same topic shouldn't merge).
- Already-superseded rows are excluded — they're tombstones, not active set members.
- Threshold is validated [0, 1].
- BFS guards against revisits via a `visited` flag set; the similarity matrix's diagonal is masked out so we don't loop back through self-edges.
- `max_clusters` cap (default 20) prevents pathological output if the working set is enormous and dense.

## Two new tools

- **`memory_compact(type=None, threshold=0.85, limit=10)`** — read-only, no Gemini call (operates on stored embeddings). Returns clusters with full member bodies so the agent can compose a merged memory.
- **`memory_supersede(old_id, new_id)`** — write, plan-approval gated. Refuses self-supersede, missing ids, and chained supersedes (old already tombstoned). Old row stays on disk for auditability; `recall` and `list` ignore it by default; `include_superseded=True` opt-in surfaces it.

System prompt documents the compaction flow: `memory_compact` → inspect clusters → one plan with `memory_save` (merged) + N `memory_supersede` (each old → new).

## Test fixtures had to use the design-default 0.85 threshold

MockEmbedder's bag-of-words math produces specific cosines for specific token overlaps. Two memories that share 7 of 8 tokens (only `name` differs) get cosine ≈ 0.93. With an aggressive 0.95 threshold the cluster algorithm correctly returned no clusters — but the test was wrong, not the algorithm. Calibrated thresholds to match the actual MockEmbedder output.

## Slice 3a — `MemoryExtractor` + `ExtractedMemoryCandidate`

`memory/extraction.py`. Reads a persisted task transcript via `WorkingMemoryStore.load_messages(task_id)`, asks the LLM to identify save-worthy moments, returns confidence-scored typed candidates with evidence quotes.

**Prompt design**: hard-coded system prompt teaches the four-type taxonomy, the body convention (rule + Why + How to apply), explicit save-vs-skip signals (corrections AND validated non-obvious choices ARE save-worthy; code patterns / file paths / git history ARE NOT), and a strict JSON output schema. "Propose at most 5 candidates per session. Quality over quantity."

**Defensive parsing**: `_parse_json_block` tries (1) plain JSON, (2) fenced code block body, (3) first balanced top-level `{...}` as a last resort. LLMs sometimes wrap JSON in `\`\`\`json` fences or chatter around it.

**Filtering**: candidates below `min_confidence` (default 0.6) are dropped before the user sees them. Candidates with bad shape (unknown type, blank fields, out-of-range confidence) are silently dropped (`_coerce_candidate` returns None). Top-K cap by confidence DESC keeps approval fatigue down.

**No agent-tool exposure**: extraction is user-invoked, not agent self-introspection. It would be circular to let the agent extract memories about itself mid-run.

## Slice 3b — `MemoryExporter` to Markdown

`memory/export.py`. Dumps memory rows to per-row Markdown files with YAML frontmatter that round-trips every column through the same `_parse_frontmatter` parser the knowledge base uses.

**Filename pattern**: `<type>__<slug>__<short-id>.md`. The short-id (last segment of the memory id) prevents collisions when two memories happen to share a slug.

**Default out dir**: `.cache/memory/exports/` (gitignored). The user passes `--out <dir>` to land files in a commit-ready location.

**Frontmatter quoting**: `_yaml_scalar` JSON-encodes any value containing YAML-significant chars (colons, brackets, etc.). This forced a backward-compatible extension to the knowledge_base frontmatter parser to handle JSON-style quoted scalars + the `null` literal — verified by the 21 existing knowledge_base tests still passing.

## Slice 3c — `MemoryPromoter` to knowledge entries

`memory/promote.py`. Drafts a `context/knowledge/entries/<category>/<slug>.md` file from a project memory. Drops `tenant_id` / `org_alias` (knowledge entries are tenant-agnostic).

**Heuristic guard for tenant-specific content**: scans the memory body + description + name + tags for:

- Mention of the source memory's `org_alias` (e.g., "AcmeProd").
- Salesforce instance URLs (regex match on `*.my.salesforce.com`, etc.).
- Multiple Salesforce-shaped IDs (15 or 18 char alphanumeric tokens; 2+ in a row strongly suggests an ID dump).
- "OrgFoo" / "SandboxFoo" / "ProdFoo" alias-shaped tokens.

Findings are warnings, not hard errors — but they soft-block the write unless `--force` is passed. `--force` still inlines the warnings into the draft as a `<!-- PROMOTION REVIEW: -->` comment so the reviewer can't miss them.

**Refuses to clobber existing files** (`FileExistsError`).
**Refuses to promote superseded memories** ("promote the replacement instead").

## CLI: `sf-agent memory <verb>`

`memory_cli.py`, dispatched from `__main__.py` via the same special-case pattern as `setup`. Three verbs:

- `memory extract --task-id <id> [--min-confidence 0.6] [--max-candidates 5]` — runs extraction, walks each candidate (yes/no/edit), persists accepted via `MemoryStore.save` with the originating task_id as `source_session_id`.
- `memory export [--type] [--out] [--cross-org] [--include-superseded]` — runs the exporter.
- `memory promote --memory-id <id> --category <cat> [--severity] [--title] [--tags] [--reference] [--force] [--out-dir]` — runs the promoter; on soft-block prints the warnings and exit code 1.

Each subcommand accepts `--db-path` for tests / non-default index locations.

## The frontmatter parser change

To let exports round-trip through `_parse_frontmatter`, the parser gained:

- JSON-style quoted scalars (`key: "value with: colons"` → `value with: colons`).
- The `null` literal (`key: null` → Python `None`).
- Block-list items also unquote JSON-style (`- "https://..."` → `https://...`).

Backward compatible — none of the 21 existing knowledge_base tests changed behavior, and all bundled `entries/**/*.md` parse identically.
