### Context Engine slice 1 — Metadata Index

A SQLite-backed, queryable snapshot of org metadata so the agent stops guessing about what exists. Designed for modularity: adding a new metadata type (ValidationRule, Flow, CustomMetadataType, LWC, etc.) requires one new parser file and zero schema changes.

#### Files added
```

├── __init__.py          # public API: build_index, ingest_directory, MetadataIndex
├── schema.sql           # generic components + relationships + index_runs tables
├── index.py             # SQLite-backed MetadataIndex (upsert, queries, run tracking)

└── parsers/

    └── custom_object.py # walks fields/ siblings; emits FIELD_OF edges
tests/test_context_index.py  # 13 unit tests, no live org needed
```

#### Schema design
Two tables, both component-type-agnostic:
- **`components`** — `(id, component_type, api_name, parent_id, file_path, source, metadata_json, last_indexed_at)`. Type-specific extracted fields live in `metadata_json` so DDL never changes.
- **`relationships`** — `(source_id, target_id, relationship_type, metadata_json)`. New edge kinds (FLOW_USES, RULE_VALIDATES, GRANTS_PERMISSION) are just new string values.
- **`index_runs`** — tracks each ingestion run for observability + delta planning.

#### Public API
```python
from sf_dev_agent.context import build_index, MetadataIndex, default_db_path

build_index(org_alias="AgentforceOrg")          # live org → SQLite
with MetadataIndex(default_db_path()) as idx:
    idx.triggers_on("Account")
    idx.fields_of("Account")
    idx.search("AccountHandler")
```

## Key design decisions

### 1. Generic schema with JSON metadata columns
Type-specific data lives in `metadata_json`, not in typed columns per component type. This means adding ValidationRule / Flow / CustomMetadataType / LWC requires zero DDL changes — only a new parser. Trade-off: queries on type-specific fields need `json_extract`, slightly slower than a typed column. Acceptable; we can add typed columns or generated columns for hot-path fields later.

### 2. Parser registry with explicit imports
Each parser registers itself at import time (`register(MyParser())`). The package `__init__.py` lists which parsers to load. Adding a new metadata type:
1. Write `parsers/<type>.py`
2. Add `from . import <type>` to `parsers/__init__.py`

Two-line change, no edits to the index core, no edits to the orchestrator.

### 3. Two-pass ingestion (components first, relationships second)
SQLite foreign-key constraints reject inserts pointing at nonexistent rows. Parsers can emit edges to components that haven't been parsed yet (e.g. `AccountHandlerExt extends AccountHandler` when files are walked alphabetically). The orchestrator buffers relationships, inserts all components in pass 1, then attempts each relationship in pass 2 — silently skipping edges whose endpoints don't resolve (e.g. trigger references to standard sObjects we didn't ingest).

### 4. `.cache/retrieve/` over `workspace/`
The workspace is the agent's *mutable working tree* — where in-flight task files get created and edited. Retrieving the full org snapshot into it would mix concerns and break multi-org indexing. The retrieve dir is a per-org staging area, separate from the workspace.

### 5. Cleanup the retrieve dir after ingestion
`build_index(cleanup_retrieve=True)` (default) wipes `.cache/retrieve/<org>/` once SQLite has the source. Eliminates filesystem duplication while keeping the separation-of-concerns. On failure the dir is preserved for debugging.

### 6. ApexClass parser uses regex, not a full AST
Lightweight extraction (class name, sharing, extends, implements, is_test). Documented as a future enhancement to swap for a real Apex AST. Acceptable for slice 1 — we get ~95 % of the value at ~5 % of the complexity.

## Future scope — refresh as a service

Documented in `src/sf_dev_agent/context/__init__.py` module docstring. The current `build_index` is a one-shot; natural evolutions are:

- **Post-deploy hook** — invoke after every successful `sf_source_deploy` so the index never lags the agent's own writes; scoped rebuild for deployed types only.
- **Scheduled refresh** — cron / scheduled agent / GitHub Action nightly to catch out-of-band changes (admins, other developers, packaged-app installs).
- **Event-driven** — poll Tooling API `SetupAuditTrail` or subscribe to a Streaming API channel; trigger delta rebuild for affected components only.
- **Delta/incremental ingest** — compare org's `lastModifiedDate` against `components.last_indexed_at`; only retrieve+parse deltas. Required for any of the above to scale beyond toy orgs.

The architecture supports all of these: parsers are independent, the index is upsert-idempotent, each ingestion run is recorded in `index_runs`. A scheduler would call `build_index(component_types=[...])` with a narrowed list and the index converges.

### 5. Apex class-reference extraction → REFERENCES edges (closes finding #2)

New shared helper `src/sf_dev_agent/context/parsers/_apex_refs.py` with `extract_class_references(source, exclude=None)`. Regex-based heuristic:
- Captures capitalized identifiers (Apex class-name convention)
- Strips line/block comments and string literals before scanning so commented-out and stringified class names don't leak in
- Filters Apex/Salesforce built-ins (`System`, `Database`, `Schema`, `Test`, `JSON`, `Math`, …), generic collection types (`List`, `Map`, `Set`), Apex primitives (`String`, `Integer`, …), common standard sObjects (`Account`, `Contact`, …), Apex annotations, and SOQL keywords
- Filters all-caps tokens (likely SOQL keywords or constants)

Both `ApexClassParser` and `ApexTriggerParser` now call the helper and emit `REFERENCES` edges to each non-built-in target. The orchestrator's existing FK-skip behavior silently drops edges to anything that isn't actually in the index. Each parser also records the extracted reference list under `component.metadata.references` for direct inspection.

Self-reference suppression:
- A class doesn't emit `REFERENCES` to its own name
- Parent (already covered by `EXTENDS`) and interfaces (already covered by `IMPLEMENTS`) are excluded from the reference list — no double-counting
- A trigger doesn't emit `REFERENCES` to its target sObject (already covered by `TRIGGERS_ON`)

**Tests:** 9 unit tests in `tests/test_apex_refs.py` cover the extractor directly (static method calls, constructors, type declarations, builtin filtering, comment/string exclusion, exclude-list behavior). 3 new integration tests in `tests/test_context_index.py` verify edges land in the index, that `EXTENDS` and `REFERENCES` don't double-count, and that the metadata.references list is populated.

### Slice 2 — Vector store (next)
Substring → semantic. The smoke test's "AccountHandler" miss is the canonical motivator. Open architectural questions before coding:

- **Embedding model.** Gemini `text-embedding-004` (free with the existing `GOOGLE_API_KEY`, 768-d) vs OpenAI `text-embedding-3-small` (1536-d, paid) vs a local model (e.g. `bge-small-en`, no API). Recommendation: Gemini, since the existing key is there and we don't introduce a new dependency.
- **Vector backend.** Three options:
  - **SQLite blob column + numpy cosine sim in Python** — simplest; fits thousands of components in milliseconds; zero new dependencies. Recommended MVP.
  - **`sqlite-vec` extension** — proper indexed similarity in SQL; needs a small native dep.
  - **External (Chroma / Qdrant)** — overkill for this scale, but the "right" answer at production size.
- **Chunking strategy.** Per-component (one embedding per ApexClass) vs per-method (chunked by `void method(...) { ... }` blocks). Per-component is simpler; per-method is more accurate. Recommendation: per-component for slice 2 MVP, revisit when we have real usage signal.
- **Refresh.** Re-embedding on every `build_metadata_index` is wasteful. Recommendation: only re-embed when `source` actually changed (compute a hash, store with the embedding).

# Wave 3 — Slice 2: Vector store + prompt tightening

Closes the substring vs semantic gap that Wave 2's smoke test surfaced (Finding #1: `code_search("AccountHandler")` returned 0 hits even though `AccountTriggerHandler` was clearly in the index).

## Architectural choices (locked at the start of Wave 3)
- **Embedder**: Gemini `gemini-embedding-001` (3072-d native; supports MRL truncation to 1536/768). Reuses the existing `GOOGLE_API_KEY` — no new key. Initially attempted `text-embedding-004` and got a 404 — it's been deprecated.
- **Vector backend**: SQLite `BLOB` column on `components` + numpy cosine sim in Python. Zero new infra; thousands of components in milliseconds. Sufficient until tens of thousands of rows.
- **Chunking**: per-component (one embedding per ApexClass / ApexTrigger / CustomObject / CustomField). Embedded text = `f"{component_type} {api_name}\n{source}"` so name-similarity AND body-similarity both contribute to ranking.
- **Refresh**: hash-gated. The text we embed is hashed (SHA-256, stored in `embedded_source_hash`); on subsequent runs we skip rows whose hash matches.

## Schema migration in place
The new columns (`embedding`, `embedded_source_hash`) are added via idempotent `ALTER TABLE` in `MetadataIndex._migrate()`, so existing index DBs upgrade in place — no rebuild required. SQLite has no `ADD COLUMN IF NOT EXISTS`, so the migration swallows the duplicate-column `OperationalError` and re-raises anything else.

## Two new agent-facing tools

### `semantic_search(query, component_type?, limit=10, min_score=0.0)`
Embeds the query (using Gemini's RETRIEVAL_QUERY task type — different optimization than the document side), computes cosine similarity against every embedded component, returns top-k. Each hit carries a `score` in [0, 1]. If everything falls below `min_score`, the response includes `best_score_below_threshold` so the agent knows the strongest candidate even when filtered out — useful diagnostic for "no, the org really doesn't have this" answers.

### `embed_metadata_index(component_types?, force=False)`
Populates / refreshes embeddings. Hash-gated by default: if `embedded_source_hash` matches the current source's hash, skip. `force=True` re-embeds everything (use after switching models — different dim ⇒ stored vectors aren't comparable to new query vectors). Returns a per-type coverage report: `{ApexClass: {total: 4, embedded: 4}, ...}`.

Both tools are in `_SF_TOOLS` so mock-org mode intercepts them — no API quota burned in offline testing.

# Wave 4 — Delta refresh

Closes the largest scaling concern from the original backlog: every prior `build_metadata_index` did a full org retrieve regardless of how stale the index actually was. With ~5 components in the test org that's invisible; with thousands of classes in a real client org it's prohibitive on every loop. Delta refresh narrows each rebuild to "only what actually changed."

## Approach

The architecture already had the foundations: `components.last_indexed_at` per row, idempotent upserts, `index_runs` tracking. What was missing was the actual delta math. New `delta.py` module:

```
src/sf_dev_agent/context/delta.py
  OrgComponent       # one row from a Tooling-API inventory query
  OrgInventory       # all components in the org, grouped by type
  DeltaPlan          # to_fetch / to_delete / unchanged / unsupported_types
  fetch_org_inventory(alias, types)  # sf data query --use-tooling-api
  compute_deltas(inventory, indexed, requested_types)
  SUPPORTED_DELTA_TYPES = {"ApexClass", "ApexTrigger"}
```

For each supported type, the planner pulls `(Id, Name, LastModifiedDate)` via Tooling-API SOQL once, compares ISO-8601 timestamps lexicographically against the index's `last_indexed_at`, and classifies each component:

- **to_fetch** — new (not in index) OR modified (`org.LastModifiedDate > last_indexed_at`)
- **to_delete** — present in index but absent from inventory (and only for types we actually queried — we don't wipe rows of types we didn't ask the org about)
- **unchanged** — skip entirely

CustomObject deltas are non-trivial (EntityDefinition queries, namespace handling, child fields/validation rules need their own deltas) and explicitly deferred. Unsupported types fall back to the existing full-retrieve path *in the same call* — so a build asking for `["ApexClass", "CustomObject"]` runs delta for ApexClass and full-fetch for CustomObject, and both ingest into the same DB in one pass so relationship resolution sees everything together.

## Targeted retrieve

`retriever.retrieve_components(org_alias, component_ids, target_dir)` accepts a list of canonical `Type:Name` IDs and passes each as a separate `--metadata Type:Name` flag. Same scaffold-the-sfdx-project + JSON-output pattern as the bulk retrieve.

## `build_index` orchestration

Public API didn't change shape — just gained a `delta=True` (default) kwarg. The orchestrator now splits requested types into delta-supported vs unsupported, runs both paths into the same staging dir, and prunes deletions from the index *before* ingestion (so a re-created component isn't accidentally orphaned). The agent-facing `build_metadata_index` tool gained a `full_refresh: bool` parameter as an escape hatch and now reports `delta_mode`, `components_fetched`, `components_deleted`, and `components_unchanged` in its result.

## Embeddings interaction

The embedding hash-gate (Wave 3) and the timestamp-gate (Wave 4) compose cleanly without explicit coordination:

1. Delta refresh re-fetches a class because its `LastModifiedDate` advanced.
2. The fresh source is upserted (overwrites `source`, bumps `last_indexed_at`).
3. Next `embed_metadata_index` run computes the new source hash, sees it differs from `embedded_source_hash`, and re-embeds *just that one row*.
4. Unchanged components flow through both gates — no retrieve, no embed, no work.

Net effect: a typical post-deploy "refresh + re-embed" sequence costs one Tooling API SOQL + zero retrieves + zero embedding API calls when the deploy didn't change source the index covers.

# Wave 5 — Slice 3: Knowledge base

Completes the hybrid context engine from the original project summary. The metadata index (Wave 1) answers "what's in this org?". The vector store (Wave 3) makes that index searchable by concept. The knowledge base (Wave 5) answers a different question entirely: **"what does Salesforce say is the right way to do this?"** — governor limits, anti-patterns, best practices, and architectural patterns that apply to any org.

## Architecture

Separate `knowledge_entries` SQLite table alongside `components`. Same embedding shape as Wave 3 (BLOB column + content-hash gate), reusing the Embedder layer. Content ships as Markdown files with YAML frontmatter, bundled at `src/sf_dev_agent/context/knowledge/entries/<category>/*.md`. On first `KnowledgeBase` open the table is empty, so `auto_load_if_empty()` ingests every bundled file. Subsequent opens are a no-op unless content changed.

Frontmatter format kept deliberately small — flat keys, inline lists, block lists. No PyYAML dependency; we own the parser (~30 lines in `knowledge/store.py`).

```
src/sf_dev_agent/context/knowledge/
├── __init__.py
├── store.py                     # KnowledgeBase + frontmatter parser
└── entries/
    ├── governor_limits/         # 10 entries
    ├── anti_patterns/           # 8 entries
    ├── best_practices/          # 8 entries
    └── patterns/                # 6 entries
                                 # 32 total
```

## Bundled content (32 entries)

**Governor limits (10):** SOQL 101, DML 150, heap 6/12 MB, CPU 10/60s, SOQL rows 50k, callouts 100/120s, async jobs 250k, future calls 50, batch chunk 200, view state 170 KB.

**Anti-patterns (8):** SOQL/DML in loops, `SeeAllData=true`, hardcoded IDs, `without sharing` as default, FLS/CRUD bypass, describe inside loops, multiple triggers per object, callout after DML.

**Best practices (8):** bulkified trigger handlers, `TestDataFactory` pattern, Custom Metadata Types for config, meaningful test assertions, sandbox-first deployment + validate-only, null-safe SOQL access (`?.` operator), trigger recursion control, Named Credentials for callouts.

**Patterns (6):** TriggerHandler base class, Selector/Service/Domain layers (fflib), Queueable chaining for long-running async, Platform Events for decoupling, LWC `@wire` vs imperative, Flow vs Apex decision guide.

Every entry has `id`, `title`, `category`, `severity`, `tags[]`, `references[]` (URLs to canonical sources — developer.salesforce.com, well-architected.framework, fflib repo, kevinohara80/sfdc-trigger-framework), and a 150-300 word body. The body covers what / why / example / when.

## Two new agent-facing tools

### `knowledge_search(query, category?, limit=5, min_score=0.0)`
Embeds the query (Gemini's `RETRIEVAL_QUERY` task type), cosine-sim ranks against every embedded entry. Returns `{id, title, category, severity, tags, references, body, score}` per hit. `min_score` threshold + `best_score_below_threshold` diagnostic for "no good match" cases — same pattern as `semantic_search`.

### `embed_knowledge_base(category?, force=False)`
Auto-loads bundled entries (if not already in DB) and populates embeddings. Hash-gated: re-running is cheap when nothing changed. `force=True` for after-model-switch rebuilds.

Both tools are in `_SF_TOOLS` so mock-org mode intercepts them — offline agent runs don't burn Gemini quota.

## Idempotency contract (deliberate redundancy with Wave 3)

The hash-gated embedding pattern from Wave 3 is duplicated, intentionally. `MetadataIndex.embed_components` and `KnowledgeBase.embed_entries` are 90% the same function. I considered factoring out a shared `EmbeddingTable` mixin but chose duplication for now because:

- The two tables differ in what gets *into* the embedding text (component types vs knowledge categories + tags), so an abstraction would mostly be parameter-passing.
- Each implementation is short (~50 lines) and fully tested.
- A mixin would couple two storage shapes that may diverge — knowledge entries might gain a `version` field, source-language tags, or different similarity metrics down the line.

If a third embedding-backed table appears, factor at that point.
