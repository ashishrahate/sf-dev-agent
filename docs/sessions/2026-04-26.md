### Context Engine slice 1 — Metadata Index

A SQLite-backed, queryable snapshot of org metadata so the agent stops guessing about what exists. Designed for modularity: adding a new metadata type (ValidationRule, Flow, CustomMetadataType, LWC, etc.) requires one new parser file and zero schema changes.

#### Files added
```
src/sf_dev_agent/context/
├── __init__.py          # public API: build_index, ingest_directory, MetadataIndex
├── schema.sql           # generic components + relationships + index_runs tables
├── index.py             # SQLite-backed MetadataIndex (upsert, queries, run tracking)
├── retriever.py         # `sf project retrieve start` wrapper
└── parsers/
    ├── __init__.py      # registry; add new parser = 1 file + 1 import line
    ├── base.py          # Parser ABC + ParsedComponent / ParsedRelationship dataclasses
    ├── apex_class.py    # extracts sharing model, extends, implements, is_test
    ├── apex_trigger.py  # extracts target object + events; emits TRIGGERS_ON edge
    └── custom_object.py # walks fields/ siblings; emits FIELD_OF edges
tests/test_context_index.py  # 13 unit tests, no live org needed
```

#### Schema design
Two tables, both component-type-agnostic:
- **`components`** — `(id, component_type, api_name, parent_id, file_path, source, metadata_json, last_indexed_at)`. Type-specific extracted fields live in `metadata_json` so DDL never changes.
- **`relationships`** — `(source_id, target_id, relationship_type, metadata_json)`. New edge kinds (FLOW_USES, RULE_VALIDATES, GRANTS_PERMISSION) are just new string values.
- **`index_runs`** — tracks each ingestion run for observability + delta planning.

#### Public API
```python
from sf_dev_agent.context import build_index, MetadataIndex, default_db_path

build_index(org_alias="AgentforceOrg")          # live org → SQLite
with MetadataIndex(default_db_path()) as idx:
    idx.triggers_on("Account")
    idx.fields_of("Account")
    idx.search("AccountHandler")
```

## Key design decisions

### 1. Generic schema with JSON metadata columns
Type-specific data lives in `metadata_json`, not in typed columns per component type. This means adding ValidationRule / Flow / CustomMetadataType / LWC requires zero DDL changes — only a new parser. Trade-off: queries on type-specific fields need `json_extract`, slightly slower than a typed column. Acceptable; we can add typed columns or generated columns for hot-path fields later.

### 2. Parser registry with explicit imports
Each parser registers itself at import time (`register(MyParser())`). The package `__init__.py` lists which parsers to load. Adding a new metadata type:
1. Write `parsers/<type>.py`
2. Add `from . import <type>` to `parsers/__init__.py`

Two-line change, no edits to the index core, no edits to the orchestrator.

### 3. Two-pass ingestion (components first, relationships second)
SQLite foreign-key constraints reject inserts pointing at nonexistent rows. Parsers can emit edges to components that haven't been parsed yet (e.g. `AccountHandlerExt extends AccountHandler` when files are walked alphabetically). The orchestrator buffers relationships, inserts all components in pass 1, then attempts each relationship in pass 2 — silently skipping edges whose endpoints don't resolve (e.g. trigger references to standard sObjects we didn't ingest).

### 4. `.cache/retrieve/` over `workspace/`
The workspace is the agent's *mutable working tree* — where in-flight task files get created and edited. Retrieving the full org snapshot into it would mix concerns and break multi-org indexing. The retrieve dir is a per-org staging area, separate from the workspace.

### 5. Cleanup the retrieve dir after ingestion
`build_index(cleanup_retrieve=True)` (default) wipes `.cache/retrieve/<org>/` once SQLite has the source. Eliminates filesystem duplication while keeping the separation-of-concerns. On failure the dir is preserved for debugging.

### 6. ApexClass parser uses regex, not a full AST
Lightweight extraction (class name, sharing, extends, implements, is_test). Documented as a future enhancement to swap for a real Apex AST. Acceptable for slice 1 — we get ~95 % of the value at ~5 % of the complexity.

### Bugs found and fixed during validation
1. **`sf project retrieve start` requires the `force-app` directory to exist** before running. Retriever now creates `force-app/main/default/` before invoking the CLI.
2. **This sf CLI version doesn't accept comma-separated `--metadata` values.** Switched to repeated `--metadata` flags (`--metadata ApexClass --metadata ApexTrigger ...`).
3. **ApexClass regex didn't handle generics in the `implements` clause** (`Database.Batchable<sObject>`). Loosened the charset to consume up to the opening brace.

## Future scope — refresh as a service

Documented in `src/sf_dev_agent/context/__init__.py` module docstring. The current `build_index` is a one-shot; natural evolutions are:

- **Post-deploy hook** — invoke after every successful `sf_source_deploy` so the index never lags the agent's own writes; scoped rebuild for deployed types only.
- **Scheduled refresh** — cron / scheduled agent / GitHub Action nightly to catch out-of-band changes (admins, other developers, packaged-app installs).
- **Event-driven** — poll Tooling API `SetupAuditTrail` or subscribe to a Streaming API channel; trigger delta rebuild for affected components only.
- **Delta/incremental ingest** — compare org's `lastModifiedDate` against `components.last_indexed_at`; only retrieve+parse deltas. Required for any of the above to scale beyond toy orgs.

The architecture supports all of these: parsers are independent, the index is upsert-idempotent, each ingestion run is recorded in `index_runs`. A scheduler would call `build_index(component_types=[...])` with a narrowed list and the index converges.
