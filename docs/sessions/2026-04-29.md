## What was delivered

### D.1 — ValidationRule parser

**`src/sf_dev_agent/context/parsers/validation_rule.py` (new)**: handles `*.validationRule-meta.xml`. Owning object is inferred from the path (`objects/<X>/validationRules/<rule>.validationRule-meta.xml` — parser pulls `<X>` from `path.parents[1]`). Top-level component (no `parent_id`) so file-walk order can't trip the FK constraint; the link to the object travels via a `VALIDATES_ON` relationship instead.

**Metadata extracted**: `active`, `description`, `error_condition_formula`, `error_message`, `error_display_field`, plus the resolved object name. Falls back gracefully on XML parse error (still emits the component with `parse_error` recorded).

**Tests**: 2 — extraction + relationship shape; orphan-path tolerance (a misplaced rule still parses, just with no edge).

### D.2 — RecordType parser

**`src/sf_dev_agent/context/parsers/record_type.py` (new)**: same shape as ValidationRule with `RECORD_TYPE_OF` edge. Metadata: `active`, `label`, `description`, `business_process` (the last is null for objects that don't use it). Path traversal uses `recordTypes/` instead of `validationRules/`.

**Tests**: 1 — full extraction + relationship shape.

### D.3 — Flow parser

**`src/sf_dev_agent/context/parsers/flow.py` (new)**: handles `*.flow-meta.xml`. Top-level component. Pulls four classes of structural fact:

- **`start.object`** for record-triggered flows → `TRIGGERS_ON` edge to the CustomObject (matches the ApexTrigger pattern).
- **`actionCalls` with `actionType=apex`** → `REFERENCES` edges to the named ApexClass (these classes implement `@InvocableMethod`).
- **`recordCreates` / `recordUpdates` / `recordLookups` / `recordDeletes`** → `REFERENCES_OBJECT` edges (deduped against `start_object` so a record-triggered flow that also writes its own object isn't double-counted).
- **`subflows`** → `REFERENCES_FLOW` edges.

**Metadata**: label, processType, status, interviewLabel, start_object, record_trigger_type, trigger_type, plus sorted lists of apex_action_classes / record_objects / subflows for cheap inspection.

**Side fix**: `MetadataIndex.triggers_on()` was unfiltered by component_type, so a record-triggered Flow's `TRIGGERS_ON` edge would have surfaced alongside ApexTriggers — breaking the existing semantics. Narrowed the SQL to `c.component_type = 'ApexTrigger'`. Docstring already said "Return every ApexTrigger…", so the contract is preserved; updated to note Flow's separate edge.

**Tests**: 2 — record-triggered with Apex action + Contact write; autolaunched flow with no `start_object`.

### D.4 — LWC parser

**`src/sf_dev_agent/context/parsers/lwc.py` (new)**: bundle-shaped. The dispatcher walks files individually, so the parser triggers off the `*.js-meta.xml` marker — but only when `path.parent.name == bundle_name`, which guards against grabbing CustomField metadata files (those use `.field-meta.xml`, but a defensive check is cheaper than a future bug).

On a hit, it reads the sibling `<bundle>.js` and extracts:
- `@salesforce/apex/<ClassName>.<methodName>` → REFERENCES edge to the ApexClass.
- `@salesforce/schema/<Object>[.<Field>]` → REFERENCES_OBJECT edge to the CustomObject (and field captured in metadata).

**Metadata**: api_version, is_exposed, master_label, description, targets list, has_html, has_css, apex_imports, schema_objects, schema_fields. Combined `source` field concatenates the meta-xml + JS + HTML so the embedder gets one coherent document per bundle.

**Tests**: 2 — full bundle extraction (including Account.Region__c schema field); guard test ensuring `*.field-meta.xml` does NOT match LWCParser.handles().

### D.5 — REPL UI v1

**`src/sf_dev_agent/repl_ui.py` (new)**: centralizes how tool calls render so `agent.py:_execute_tool` doesn't sprinkle ad-hoc `console.print` calls.

Shipped functions:
- `render_tool_call_header(name, input)` — `┌ <name>  key=value, key=value` header line.
- `render_tool_ok(name, result)` — `└ ✓ <name> → N chars` footer.
- `render_tool_error(name, msg)` — `└ ✗ <name> <truncated msg>` footer.
- `render_tool_blocked(name, reason)` — `└ ⊘ <name> blocked <reason>` footer for write-tool gating.
- `tool_status(name)` — context manager wrapping `console.status()` with a spinner; no-ops cleanly when the console isn't a TTY (tests, piped runs).
- `format_tool_input_summary(input, max_len=120)` — compact `key=value` form, collapses multi-line / long-string values to `<str N chars>`, lists to `<list N>`, nested dicts to `<dict N keys>`. Truncates with an ellipsis when the joined summary exceeds `max_len`.
- `render_streaming_text` / `render_stream_terminator` — small wrappers used by the `on_text` callback so the streaming path goes through the same module.

**Wired into `agent.py`**: replaced the four `console.print` patterns in `_execute_tool` (header / blocked / OK / error) with the new helpers. Tool execution is now wrapped in `with tool_status(tool_name):` so even synchronous tools get a spinner — this matters most for `build_metadata_index` and the first-time `semantic_search` call which can take 30s+.

**Design choice — module-level shared console.** `repl_ui` keeps a single `Console` instance (swappable via `set_console_for_tests`) so the spinner and the printed lines coordinate properly. Tests substitute a `Console(file=StringIO, force_terminal=False)` and assert on the captured text.

**v2 deferred** (logged in ROADMAP):

- Collapsible tool blocks via rich `Group`/`Tree`.
- Syntax-highlighted code in tool results (rich `Syntax`).
- Prettier slash-command help.

**Tests**: 12 — input-summary edge cases (key=value form, long strings, lists, dicts, truncation, non-dict fallback, empty); each lifecycle renderer (header, ok, error, blocked) emits the expected glyph + name + content; `tool_status` no-op behavior in non-terminal mode; streaming text writes deltas + terminator.

## Architectural choices locked in D-series

- **New child-of-CustomObject metadata types use `VALIDATES_ON` / `RECORD_TYPE_OF` edges, not `parent_id` FKs.** ValidationRule and RecordType could have used `parent_id` like CustomField does — but CustomField is co-emitted from the CustomObject parser in the same `ParseResult`, so its parent always exists at upsert time. ValidationRule and RecordType live in their own files, dispatched independently, with FS-dependent walk order. Going edge-only sidesteps the FK ordering risk while keeping graph queries expressive.
- **Flow's `TRIGGERS_ON` is a distinct semantic from ApexTrigger's, but the edge type is shared.** A record-triggered flow IS a trigger on that object — same conceptual relationship. Differentiating is a query-time concern, not a schema concern. `triggers_on()` filters to ApexTrigger by name; future `flows_on()` would do the symmetric thing for Flow.
- **LWC bundles are represented as one component per bundle, not per file.** The `.js`, `.html`, `.css`, `.js-meta.xml` are all aspects of a single deployable unit. The combined `source` field gives the embedder one coherent document and lets `code_search` find a bundle by anything in any of its files.
- **REPL UI is a separate module with a swappable console.** `agent.py` doesn't own console state any more — it imports renderers. This makes UI changes (v2 inline diffs, syntax highlighting) localized to one file.
- **Spinner is opt-in to TTY context.** `tool_status()` checks `console.is_terminal` and no-ops otherwise. CI runs, piped output, and tests all skip the spinner cleanly without conditional callsites.
